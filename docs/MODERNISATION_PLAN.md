# Modernisation plan: ProductImageProcessSystem as a CV example

Status: proposed, nothing implemented yet.

## Goal

Make this roughly nine-month-old repo a credible example of **spec-driven agentic development**: a system almost entirely generated by Claude Code from specs and prompts, then verified by a human-designed guardrail of tests and CI. Changes stay small and reviewable. No large rewrites without explicit agreement.

## Positioning

Keep two statements separate.

**What the system is:** a multimodal product-image retrieval pipeline. Images are cleaned, embedded with CLIP (ViT-B-32 by default, ViT-L-14 optional; text and image share one space), searched through a vector database and clustered with DBSCAN. Quality is scored with a learned aesthetic predictor.

**How it was built:** almost entirely generated by Claude Code, directed by a written spec and verified by tests.

Tagline (for the README and CV):

> A multimodal product-image pipeline (CLIP embeddings, vector search, clustering), built almost entirely with Claude Code from specs and prompts, then verified with tests and CI.

### The method: spec-driven agentic development

| Part | Meaning | Evidence in the repo |
|---|---|---|
| Spec | The human directs with intent and constraints, not by typing code | `CLAUDE.md` (architecture, rules, thresholds), the design decision "preprocess before embedding" |
| Agent | Claude Code writes, runs and iterates on the code | `Co-Author: Claude` headers in about 15 files |
| Guardrails | The human acts as architect and reviewer, with checks that catch agent mistakes | Tests and CI (Tier 1, not yet built) |

### Claims to avoid

- **RAG and prompt engineering:** the repo makes no LLM calls, so neither applies. (A real RAG feature is possible; see item 10.)
- **"Fully" or "all code" generated:** use "almost entirely". Any hand edits make "all" untrue, and the two-commit git history cannot prove it either way.
- **"Vibe coding":** it implies unreviewed code.

## What the repo has and lacks

Has: a clear architecture with a documented design decision, lazy-loaded model caching, two swappable vector DB backends, a FastAPI web layer, Docker, and a `CLAUDE.md`.

Lacks:
- **Tests:** there is no `tests/` directory. This is the biggest gap, because the guardrail is half of the method.
- **CI:** there is no `.github/workflows`.
- **Health endpoint and logging:** neither exists, so there is no observability story.
- **A likely broken Docker healthcheck:** it imports `requests`, which is not in `requirements.txt`.
- **Dockerfile hygiene:** it is labelled multi-stage but is not, it runs as root, and `docker-compose.yml` has the obsolete `version:` key.
- **Dependency pinning:** most packages use `>=` ranges, so builds are not reproducible.
- **Provenance:** git history is two commits by one author, and the only evidence of agent authorship is self-declared headers.
- **Positioning:** there is no README section aimed at a reviewer.

## Tier 1: small, low risk (about 1 day)

1. **Tests with pytest.** Add about 15 to 25 fast tests that need no model downloads:
   - schema validation, `SessionManager`, `InMemoryVectorDB`, clustering, the similarity-threshold logic
   - the basic quality scorer on synthetic images
   - FastAPI routes via `TestClient`, with the pipeline service mocked
2. **GitHub Actions CI.** Run `ruff` and `pytest` on push and pull request, and build the Docker image.
3. **`/health` endpoint plus structured logging.** Point the Docker healthcheck at it, with no extra dependency.
4. **Dockerfile and compose cleanup.** Use a non-root user, a real multi-stage build, and drop the `version:` key and the commented-out environment lines.
5. **Pin dependencies.** Add a lock file (or `requirements.lock`) and a `pyproject.toml` with ruff and pytest config.
6. **README rewrite.** Open with the tagline above, then a one-paragraph result, an architecture diagram, a quickstart, and a "Built with spec-driven agentic development" section that links to the workflow doc.

6b. **Faster deployment (model footprint), added later.** Make `ViT-B-32` (`openai`) the default embedding model, keep `ViT-L-14` as an opt-in through `CLIP_MODEL` and `CLIP_PRETRAINED`, and bake the CLIP and U2Net weights into the Docker image at build time. See "Model footprint" below.

## Model footprint (deployment speed)

Findings:
- No library ships weights. `open_clip` downloads CLIP from Hugging Face on first use (ViT-L-14 is about 1.7 GB, ViT-B-32 about 350 MB) and `rembg` downloads U2Net (about 170 MB) from a GitHub release. "Pre-installed with the library" is not possible.
- The image build only runs `pip install`. Weights are fetched when the container first starts, which is the slow part of deployment.
- `clip_aesthetic_scorer.py` already defaults to ViT-B-32 and scores with zero-shot text prompts, so changing the embedding model does not break quality scoring.

Decisions:
- **Default model: ViT-B-32 (`openai`), 512 dimensions.** ViT-L-14 (768 dimensions) stays available as an opt-in. Trade-off: lower accuracy (ImageNet zero-shot about 63% against 75%), and existing Milvus collections built with ViT-L-14 are refused by the model-mismatch guard and must be rebuilt.
- **Bake weights into the image.** A build-stage `RUN` downloads the CLIP and U2Net weights into a fixed cache directory, the runtime stage copies it, and `HF_HUB_OFFLINE=1` stops runtime network calls. This also removes the Hugging Face "unauthenticated requests" warning without using any token.
- **No personal tokens, ever.** The repo is public: no `HF_TOKEN` in the Dockerfile, compose file, CI or `.env` committed to git. Anonymous downloads of public models are enough.

## Refactor tier: code-quality follow-up (between Tier 1 and Tier 2)

Tier 1 is done. A review of the result rated the code quality mixed: path traversal risk in session IDs, blocking calls inside async routes, about 40 blanket `except Exception` blocks, scattered configuration, module-level `torch` imports and thin test coverage outside the basics. The ten small steps, in three groups (P0 safety, P1 configuration and lint, P2 testability), are in `docs/REFACTOR_PLAN.md`, one commit each, with no restructuring of `src/`.

Do this before Tier 2. The typed-settings item below builds on step 4 of the refactor plan, and the evaluation script (item 9) is more trustworthy once the pipeline has tests.


7. **`docs/SPEC_DRIVEN_WORKFLOW.md`.** Document the real method: how `CLAUDE.md` steers the agent, how tasks were prompted (task, constraints, iteration), what the tests catch, and what was corrected by hand. Needs the owner's real details and the honest "almost entirely" share; nothing is invented. If details are not supplied it stays a template.
8. **`docs/PROMPTS.md`.** Representative original prompts, only if they were kept or can be honestly reconstructed and labelled as such.
9. **Small evaluation script.** Measure the 90% and 70% similarity thresholds on a few labelled sample pairs and report precision and recall.
10. **Typed settings.** Replace scattered `os.getenv` calls with a `pydantic-settings` class in `src/pipeline/config.py`. (Refactor step 4 first centralises the values as plain constants; this item upgrades that to typed settings.)
11. **Optional real RAG feature.** Retrieve the top-k similar products from the vector DB, pass them and the cleaned image to the Claude API, and generate a product listing or a duplicate explanation. Behind a flag, with a mocked test. Only after this exists may the README say "RAG".
